## 1. Why this one is different

P8.3's output was internal: an attempt lifecycle nothing outside `learning` can see. P8.4's
output is three things other people consume.

| What lands here | Who is waiting |
|---|---|
| `learning.ProgressReader` | `gamification`, `admin`, `analytics` — all Phase 3 |
| `learning.UnlockChecker`, batched | `lesson`, **today**, where a nil unlocker means every lesson is unlocked |
| Next-activity resolution | The dashboard's hero card, and the answer to the UI plan's question 1 |

Two of the three are contracts P8.1 froze and nobody has implemented. The third has no contract
and no endpoint yet — P8.5 renders it — so its shape is entirely yours to get right, and the
states it can be in are the states the client has to render.

The bar: **`lesson` stops carrying its own copy of the unlock question, and the rollup stops
telling learners they finished a course they did not.**

## 3. Trap 1 — the unlock question needs data from both modules, and neither owns both halves

`UnlockChecker.IsUnlocked(ctx, userID, lessonIDs) (map[uuid.UUID]bool, error)` lives in
`learning`'s contract, and `learning` cannot answer it alone:

| Half of the answer | Table | Owner |
|---|---|---|
| Which lessons a lesson requires, and at what `min_score` | `learn.lesson_prerequisites` | `lesson` |
| Whether this learner completed them, and with what score | `learn.progress` | `learning` |

`learn.lesson_prerequisites` is `lesson`'s table, created in `db/migrations/lesson/`, and it
carries `min_score`. So "unlocked" is not "the prerequisite lesson is complete" — it is
**complete and scored at or above `min_score`**. A checker that ignores `min_score` passes every
test written against seed data that sets no minimum, and silently unlocks the product.

Same shape as P8.3's Trap 1, same rules. `m_learning_service` may depend on `c_lesson`
(`.go-arch-lint.yml:386`), so read prerequisites through `lesson`'s contract, never with SQL.
`lesson`'s `Reader` does not expose them yet; `db/queries/lesson/prerequisites.sql` already has
`ListPrerequisitesForLessons`, batched, which is the query behind whatever you add.

Three things about the direction of the call:

- **It is a cycle, and that is expected.** `lesson` asks `learning` whether a lesson is
  unlocked; `learning` asks `lesson` what the prerequisites are. It terminates because the two
  methods are different — keep it that way deliberately: whatever `lesson` exposes for
  prerequisites must not itself consult the unlocker.
- **`m_lesson_service` may not depend on `c_learning`**, and must not start. `lesson` keeps its
  locally declared consumer interface; only its **signature** changes, to the batched one. That
  is the adoption the handoff notes promise lands in one diff with P8.4 — both sides, this PR.
- **`cmd/api` builds `lesson` before `learning`, and now each needs the other.** `lazyGuard` at
  `cmd/api/modules.go:275` is the pattern already in the file for exactly this: resolve on call,
  not on construction. Do not reorder the composition root and do not build either module twice.

Batched means batched. `evaluateLock` runs once per lesson when a course listing renders, and a
checker that loops internally moves the N+1 rather than removing it. One prerequisite read and
one progress read for the whole slice.

## 4. Trap 2 — the enrolment status the spec promises cannot be stored

Read these two lines together before writing `Enroll`:

```
api/openapi/components/learning.yaml:16   enum: [active, completed, paused]
db/migrations/learning/1700000210_*.sql   CHECK (status IN ('active', 'completed', 'dropped'))
```

`paused` cannot be written. `dropped` cannot be returned. Both were merged, in different tasks,
and nothing in CI compares them — no linter here reads a CHECK constraint against an OpenAPI
enum.

The two values legal on both sides are `active` and `completed`, and Phase 2 needs no others:
nothing in this task pauses or drops an enrolment. **Take that, or reconcile the two
deliberately, and record which in `DECISIONS.md`.** What is not acceptable is code that can emit
a value the other side rejects, discovered by a learner.

The same table has a coupling that will catch the rollup in §5:

```sql
CHECK ((status = 'completed' AND completed_at IS NOT NULL)
    OR (status <> 'completed' AND completed_at IS NULL))
```

Completing an enrolment sets both columns or the write fails. And `uq_enrollments_user_course`
makes a second enrolment a conflict, which is why `409` is on the operation in the spec — return
it as an `apperr` with a code, not as a raw unique-violation error.

## 5. Trap 3 — the course completes when the last lesson does, and that is not the same thing

`rollupCourse` (`service/service.go:617`) decides a course is finished like this:

```go
nextLesson, err := s.lesson.NextLesson(ctx, activity.CourseID, &activity.LessonID)
if nextLesson == nil { /* course complete, publish course.completed */ }
```

That asks *"is this the last lesson in the course?"*, not *"is every unit in this course
complete?"*. Reproduce it before you change it:

> A course with three units. The learner does nothing in units 1 and 2, opens unit 3 and
> completes it. Unit 3 rolls up complete — correctly, it is. Its final lesson has no next
> lesson, so `course.completed` is published and `progress(scope=course)` is written
> `completed`, with two thirds of the course untouched.

`course.completed` is consumed by Phase 3's `gamification` and `analytics`. An event that is
wrong is worse than an event that is missing, and this one is wrong in the direction that awards
a certificate.

BR-LEARNING-06 is a rule about scopes, not about position: a course is complete when **every
unit in it is complete**, the way a unit is complete when every lesson is — which
`rollupUnitAndAbove` already does correctly with `ListProgressByUserScopeAndIDs`. The missing
piece is the course's unit list, which is `lesson`'s to answer; §3 is already opening `lesson`'s
contract, so resolve both needs in one addition rather than two.

Then, and only then, the enrolment: a course that completes flips `enrollments.status` to
`completed` with its `completed_at`, inside **the same transaction** as the progress row and the
outbox write. P8.3 established that boundary. Do not open a second one.

P8.3's table-driven boundary test is where the new case belongs. It should fail against the
current code.

## 6. Trap 4 — mastery writes free text into a CHECK constraint, inside the grading transaction

`ActivityCompleted.Skill` is populated from `activity.LessonSkillFocus`
(`service/service.go:472`), and:

```
learn.lessons.skill_focus    text, CHECK (char_length BETWEEN 1 AND 50)    -- free text
learn.skill_mastery.skill    CHECK (skill IN ('vocabulary','grammar','reading',
                                              'listening','speaking','writing'))
```

A content author who types `Vocabulary`, `vocab` or `pronunciation` writes a lesson that is
perfectly valid in `lesson` and cannot be recorded in `skill_mastery`. If the mastery upsert
runs inside the grading transaction — which is where it belongs, atomic with the attempt — the
constraint violation **aborts the rollup and fails the learner's submission**, over a content
author's spelling.

So normalise and validate the skill *before* the write, and treat an unrecognised focus as "no
mastery update", logged, not as an error. The attempt grades either way. Say in the PR what an
unknown skill does and where you proved it.

Two more constraints in that table are not negotiable:

- `level ~ '^(A1|A2|B1|B2|C1|C2)$'` — mastery's level is **CEFR**, not a percentage. Your
  estimator produces a number and something has to project it onto six bands; that mapping is a
  decision to record, not a constant in the middle of a service method.
- `confidence numeric(5,2)`, between 0 and 1 — two decimal places. A test asserting `0.8333…`
  against a value read back from Postgres fails, and it is not the estimator's fault.

**BR-LEARNING-09 is explicit about the algorithm**: an exponentially weighted estimate over
recent attempts, *"not a raw average — recent performance must dominate"*, and WP8 adds "updated
incrementally, not recomputed from all history on every attempt". Both halves are testable and
neither is tested by a happy path. The test that carries this is **a learner who scored badly
ten times and then well three times, whose mastery moved** — under a running average it barely
would.

One tension to settle out loud: `learning/TODO.md`'s generated Phase 3 list contains "Skill
mastery estimation and the skill radar", while WP8 P8.4 requires the incremental update now and
P8.5's dashboard returns `skill_mastery`. The update is Phase 2; the radar and the adaptive plan
built on it are Phase 3. Record that reading so the next agent does not reopen it.

## 7. Trap 5 — next-activity is three states, and it needs no new contract method

WP8: *"given a learner, return the one activity they should do now"*, and the trap it names is
returning `null` with no explanation, or a 404, for a learner who has not started. The spec
already fixed the answer — `DashboardResponse.state` is `not_started | in_progress | completed`,
and `next_activity` is **absent**, not null, in two of the three. Model those states in the
domain now; P8.5 renders them.

The resolution itself is answerable with the contract as it stands after §3 and §5:
`ListEnrollmentsByUser` → the learner's lesson-scope progress → `lesson.Reader.NextLesson` and
`GetLesson`, whose `Lesson` carries `Title`, `SkillFocus`, `EstimatedMinutes` and its ordered
`Activities`. Two consequences worth knowing before you start:

- **`NextActivity.title` is the lesson's title.** `learn.activities` has no title column — it is
  `id, lesson_id, position, kind, content_version_id, config, weight` — and the spec's example,
  "Academic Word List - Topic 1", is a lesson name. Do not add a column, and do not widen
  `ActivityHierarchy` to carry a title it has nowhere to read from.
- **Do not walk the whole course tree.** One `GetLesson` per lesson in a 40-lesson course, on the
  endpoint hit at every app open, is the N+1 that P8.5's acceptance ("assert the query count")
  exists to catch — and P8.5 cannot fix what this task's shape forces on it. Resolve outward from
  the learner's current position, not downward from the course root.

`lesson` caches its tree reads (`lesson/AGENT.md` §12). Read through the contract and you inherit
that; there is no cache to add in this task.

## 8. Trap 6 — two endpoints already promise things the code does not do

**`POST /activities/{id}/attempts`.** The spec's own description reads *"Verifies unlocking
prerequisites and starts a new in-progress attempt"*. `StartAttempt` verifies that the activity
resolves, and nothing else — there was no unlocker to call in P8.3. After §3 there is, and that
sentence becomes true or the spec becomes a lie. Enrolment is the same question one level up: a
learner attempting an activity in a course they never enrolled in.

Both answers need a status code and a code in `shared/apperr`. `403` and `409` are already on the
operation, so neither needs a spec change. Follow `lesson`'s locked-lesson precedent — a
human-readable reason in `Problem.meta`, which P7 built `lockReasonFor` for. **Do not auto-enrol**
a learner who starts an attempt: enrolment is an act, it is what the `409` in §4 is about, and
creating one silently hides the bug that sent the request.

**Sessions.** Small, and there are three ways to get them wrong:

- `minutes` is computed on the server from `started_at` and `ended_at`. `CompleteSessionRequest`
  carries only `activities_completed`; a client-supplied duration is the same class of mistake as
  a client-supplied score (BR-LEARNING-01).
- A session id belonging to another learner is a `404`, not a completed session. `attempts` had
  the same trap in P8.3 — an id is not an authorisation.
- `learning.session_completed` goes to the outbox in the same transaction as the update, like
  every other event this module publishes. `ck_learning_sessions_ended_after_started` and
  `minutes >= 0` are enforced by the table; a clock that runs backwards should fail your code
  before it fails the constraint.

`StartSessionRequest.metadata` has a column — P8.2 created it precisely so this task would not
accept the field and discard it.

## 10. Acceptance

- [ ] `IsUnlocked` honours `min_score`, not just completion — a prerequisite completed *below* the
      minimum leaves the lesson locked, proven by a test
- [ ] `IsUnlocked` answers for N lessons in a bounded number of reads; assert it. A loop inside
      the implementation fails this
- [ ] `lesson` uses the batched signature, wired in `cmd/api`, with a test **in `lesson`** that a
      lesson with unmet prerequisites is reported locked with its reason. `m_lesson_service` still
      does not depend on `c_learning`
- [ ] A course completes only when **every unit** in it is complete. The unit-3-only scenario in
      §5 produces no `course.completed`, and the test fails against the current code
- [ ] Course completion sets `enrollments.status = 'completed'` with `completed_at`, in the same
      transaction as the course progress row and the outbox write
- [ ] Enrolling twice is a `409` with an `apperr` code; every status value written is legal in
      both the CHECK constraint and the OpenAPI enum, and the choice is in `DECISIONS.md`
- [ ] Mastery is exponentially weighted: the "ten bad then three good" test moves the estimate
      materially, and a running average would not pass it
- [ ] An unrecognised `skill_focus` does **not** fail the submission — the attempt still grades and
      rolls up, and a test asserts that
- [ ] Mastery is updated incrementally from the attempt outcome; nothing reads the full attempt
      history on submit
- [ ] Next-activity answers sensibly for a learner with no enrolment, a learner mid-lesson, and a
      learner who has finished everything — three tests, three explicit states, no `null` and no 404
- [ ] Resolving next-activity does not issue one lesson read per lesson in the course; say what it
      does issue
- [ ] `StartAttempt` refuses a locked activity and one in an unenrolled course, with codes and a
      human-readable reason, and does not auto-enrol
- [ ] Session `minutes` is server-computed; another learner's session id is a `404`;
      `learning.session_completed` lands in the outbox in the completing transaction
- [ ] `ProgressReader.ProgressOf` returns every row for the requested scope in one query
- [ ] `openapi.yaml` and `api/openapi/components/learning.yaml` are unchanged by this commit
- [ ] No query in `db/queries/learning/` reads a table this module does not own. Nothing automated
      checks this; say in the PR that you checked
- [ ] Coverage **≥ 85 %** on `internal/modules/learning/...`, from `make cover-check`
- [ ] `learning/AGENT.md` and `lesson/AGENT.md` `last_verified` bumped; both `TODO.md` Progress
      tables updated
