## 3. Part A — publishing a lesson

`service.PublishLesson` exists, refuses an empty lesson, refuses one whose activity points at
draft or archived content (BR-LESSON-02), flips the status in a transaction and writes
`lesson.published` to the outbox. It is correct and it is unreachable.

Nothing in Phase 2 can therefore produce a `lesson.published` event, which means **part B
cannot be tested** — you cannot prove invalidation-on-publish when nothing can publish.

### The spec changes first, in its own commit

```
POST /api/v1/admin/lessons/{id}/publish     x-permission: content.publish
```

`content.publish` is the permission `content` already uses for its own publish and archive,
and `rbac` seeds it (migration `1700000180`). Do not invent a `lesson.publish` permission;
the same people who publish material publish the lessons that carry it.

Response is `LessonDetail`, which `components/lesson.yaml` already defines. Document `409`
for `ACTIVITY_CONTENT_UNPUBLISHED` and `422` for an empty activity list — both are codes the
module already returns.

**`AGENT.md`'s endpoint table is generated.** It comes from
`tools/docgen/data/learning.json`, so adding the route means editing that file and running
`make docs`. Editing the Markdown by hand looks like it worked until `make docs-check` fails
in CI — P7.4 lost its TODO checkboxes to exactly this.

Then: `make gen-backend`, `pnpm gen:api`, the handler, the route in `AdminRoutes`, and the
entry in `cmd/api/routes_test.go`.

### What about creating units and lessons?

Leave it. `repository.CreateUnit`, `CreateLesson` and `UpdateLesson` stay reachable only from
tests until P11.1 decides whether its seed calls the repository directly or the spec grows
routes. That decision belongs to the task that has the requirement, and inventing three
endpoints nobody asked for is how an API surface doubles.

Say so in the PR, so P11.1 is not surprised.

## 4. Part B — caching, and the two traps in it

`AGENT.md` §12 names both keys and both TTLs:

| Key | TTL | Invalidated by |
|---|---|---|
| `fluentra:{env}:lesson:detail:{lesson_id}:v1` | 1 h | `lesson.published`, structure edit |
| `fluentra:{env}:lesson:catalogue:{filter_hash}:v1` | 15 min | Any publish |

Build them with `cache.Key(env, "lesson", "detail", id, 1)`. Read through
`Cache[T].GetOrLoad`, which already does singleflight, so a cold key under load calls the
loader once rather than once per request.

`m_lesson_service` does not list `p_cache` in `.go-arch-lint.yml` — P7.4 removed it when it
split the module by layer, because nothing used it. Add it back to `m_lesson_service` only.
The repository and the transport layer have no business holding a cache.

### Trap 1 — you cannot delete a key you cannot name

`Cache.Delete(keys ...string)` takes explicit keys. The detail key is fine: you know the
lesson id. **The catalogue key is not** — `{filter_hash}` means there is one key per
combination of `level`, `limit` and `offset`, and "invalidated by any publish" would need a
wildcard delete that this facade does not offer, and that `SCAN`-ing Redis in a request path
should not add.

Two honest designs:

- **A generation counter.** Keep `fluentra:{env}:lesson:catalogue:generation` in Redis, fold
  its value into the hash, and bump it on publish. Every old key becomes unreachable at once
  without deleting anything, and Redis evicts them on TTL. Costs one extra `GET` per
  catalogue request.
- **Accept the TTL.** 15 minutes is already short. Do not invalidate the catalogue at all,
  and say in the response documentation that the catalogue is up to 15 minutes stale.

Both are defensible. **Pick one, and record it in `lesson/DECISIONS.md`** — through
`tools/docgen/data/learning.json`, since that block is generated too. What is not defensible
is a `Delete` call with a key pattern in it that silently matches nothing.

### Trap 2 — invalidation is asynchronous, and the API process is not the worker

Outbox events reach subscribers through `cmd/worker`, not `cmd/api`. So a publish returns
`200` from the API, and the invalidation happens in another process a moment later. Between
those two points, `GET /courses/{slug}` serves the pre-publish tree.

That window is real and it is not automatically acceptable: an author publishes a lesson,
reloads the course, and does not see it. Decide deliberately:

- invalidate synchronously in the service as well, right after the transaction commits, and
  treat the event as the backstop for other processes; or
- accept the window and state its size.

Whichever you choose, **the test has to demonstrate the behaviour you chose**, not the one
you hoped for. A test that publishes and then reads through the same in-process service
proves nothing about a two-process system.

### Trap 3 — a cache outage is not a 500

`platform/cache` distinguishes `ErrMiss` from a Redis failure on purpose — its own comment
says a facade whose sentinel is the vendor's is not a facade. A course tree must still be
readable when Redis is down. `GetOrLoad` already falls through to the loader; make sure your
own code does not turn a `Delete` failure during publish into a failed publish.

## 5. Part C — consuming `content.archived`

`lesson/AGENT.md` §4 lists `content.archived` under events this module **consumes**, with the
purpose "flag lessons whose content was archived". Nothing subscribes to it today.

Copy the shape in `internal/modules/rbac/module.go`: a `Subscribe(bus eventbus.EventBus)`
method on `Module`, a typed payload struct, a handler, and a line in `cmd/worker/main.go`.

What "flag" means is a decision, and the schema has no column for it. The cheap and correct
version for Phase 2: **invalidate the detail cache of every lesson holding an activity bound
to that content version**, so the next read reflects reality. `ListActivitiesByLessonIDs`
exists; you need the reverse lookup — activities by `content_version_id`, which
`idx_activities_content_version_id` already serves.

Do not add a column, and do not unpublish the lesson. Archiving is discovery-only by
decision (`content/DECISIONS.md`) and a learner mid-lesson keeps reading the version they
hold — that guarantee is P7.3's and this must not quietly undo it.

## 7. Definition of Done

Everything in [phase-2-plan.md](../phase-2-plan.md) §2.3, plus the five that have each cost a
round trip already:

1. **`make check` is not the whole check.** CI runs a second lint pass that it does not:

   ```bash
   golangci-lint run --build-tags=integration ./...
   ```

2. **Coverage is measured, not estimated.** `make cover-check` needs Postgres and Redis.
   Quote the figure it printed.

3. **One task, one diff.** Formatting sweeps, dependency bumps and tool configuration each go
   in their own commit, or not in this branch at all.

4. **A test that cannot fail is not a test.** State the failure it is designed to catch, then
   check it would actually catch it. A cache test that never evicts, and a query-count fake
   that counts one method, both pass forever.

5. **A suppression comment is a claim.** `#nosec`, `//nolint`, `eslint-disable`. If the claim
   is false you have hidden a real bug from the tool built to find it. Two of these have
   already shipped in this work package — one of them was caught by CodeQL, not by review.

Before you finish:

```bash
make check
golangci-lint run --build-tags=integration ./...
make cover-check
make docs-check
```

Then update `lesson/AGENT.md` (`last_verified`), the **Progress** table in `lesson/TODO.md`
— not the generated checkboxes above it — and record the two decisions from §4 in
`learning.json`.

## 8. What this task does **not** do

- No unit or lesson creation endpoints. §3 explains why; P11.1 decides.
- No batched `IsUnlocked`. `GetCourseDetail` still calls it once per lesson, which is an N+1
  into `learning`. The interface is single-lesson because `learning/AGENT.md` §4 documents it
  that way, and **P8.1 owns that contract** — it should decide whether it takes a slice of
  lesson ids the way `content.Reader.GetManyVersions` does. Changing it from this side would
  be editing another module's published interface.
- No lesson versioning (BR-LESSON-05). Still no field in the spec, still a design decision
  rather than an implementation detail.
- No web work. WP10.
