## 1. This task ships no behaviour, and that is the whole point

No handler, no service, no migration, no table. What lands is four Go types in
`learning/contract` and eight paths in `openapi.yaml` with nothing behind them.

Two things depend on that being true:

- **WP10 starts the moment this merges.** The frontend agent builds the dashboard and the
  lesson runner against `web/src/types/api.ts` generated from this commit. That is what
  makes the two tracks parallel rather than nominally parallel (plan §2.2).
- **`ExerciseGrader` is implemented once in WP9 and five more times in Phase 3.** WP8's
  opening line is "slow down here", and this is the task it is about. Every mistake in the
  shape of these four types is paid for six times, after the point where changing it is
  cheap.

A contract-only task is not a small task. It is a cheap task to *write* and an expensive one
to get wrong.

## 4. Trap 1 — `GradeResult.ReviewItems` may not be an `srs` type

`AGENT.md` §4 says `ReviewItems` "is what feeds `srs`", and `learning/DECISIONS.md` already
records that the grader returns them. The obvious reading is
`ReviewItems []srscontract.ReviewItem`. It is wrong, and `.go-arch-lint.yml` already says so:

```
m_learning:   { mayDependOn: [..., c_srs] }        # learning may
m_vocabulary: { mayDependOn: [..., c_srs, c_learning] }
m_grammar:    { mayDependOn: [..., c_srs, c_learning] }
m_reading:    { mayDependOn: [..., c_learning] }   # no c_srs
m_listening:  { mayDependOn: [..., c_learning] }   # no c_srs
m_speaking:   { mayDependOn: [..., c_learning] }   # no c_srs
m_writing:    { mayDependOn: [..., c_learning] }   # no c_srs
```

Every one of those six modules implements `ExerciseGrader` and therefore *returns a
`GradeResult`*. If that struct carries an `srs` type, four of them reference `c_srs` through
it, and deepScan fails four Phase 3 modules for a dependency none of them asked for.

So `ReviewItem` is a **`learning`-owned type in `c_learning`**, and `srs` maps it to its own
at the boundary. `srs/contract` is empty today, so there is nothing to reuse even if the
rule allowed it — do not create one there "for WP9 to fill in". P9.1 owns that package.

Widening the arch-lint rules to grant `c_srs` to four more modules is the wrong fix, and it
is the fix that will look tempting when the linter goes red.

## 5. Trap 2 — the idempotency key is HTTP, and the spec has no machinery for one

ADR-0015 requires idempotent submission, and WP8 is explicit that the key is part of the
HTTP contract rather than a backend detail. It is also the single hardest thing to add
later: once the frontend has shipped a submit call, changing where the key travels is a
coordinated release.

Lock in `Idempotency-Key: <UUIDv7>` as a **required request header on
`POST /attempts/{id}/submit`**, and record it in `learning/DECISIONS.md` through
`learning.json`.

Two mechanical points, because the spec has never carried a request header before:

- There is no `components.parameters` section in `openapi.yaml` and no `in: header`
  parameter anywhere. Add the section rather than inlining the parameter, so P9 and Phase 3
  reuse one definition instead of three that drift. `components/headers.yaml` is for
  *response* headers — it is not the right home.
- `oapi-codegen` turns a header parameter into a params struct on the generated operation,
  and `pnpm gen:api` puts it in the TS operation type. Check both outputs actually contain
  it; a header the generators dropped is a contract that exists only in the YAML.

**This task does not implement idempotency.** P8.3 does, with the concurrency test. What
you are shipping is the promise.

## 6. Trap 3 — `IsUnlocked` is single-lesson, and `lesson` already pays for it

`lesson/TODO.md` hands you this deliberately:

> `GetCourseDetail` evaluates the lock for every lesson in the course, so a forty-lesson
> course is forty calls into `learning`. The interface is single-lesson because
> `learning/AGENT.md` §4 documents it that way; P8.1 owns that contract.

P7.5 declined to change it from the `lesson` side, correctly — that would have been editing
another module's published interface from outside. You are the other side.

The precedent is in the same tier: `content.Reader.GetManyVersions` takes a slice, and P7.4
proved the single-version version was an N+1 with a counting reader. `GetCourseDetail`
already caches the course tree, so the lock evaluation is now the *only* thing a warm
course-tree read still does per lesson.

Decide, and record it in `learning/DECISIONS.md`:

- **Batch it** — `IsUnlocked(ctx, userID, lessonIDs []uuid.UUID) (map[uuid.UUID]bool, error)`,
  or a batch method beside the single one. Costs `lesson` a small change in P8.4's wake.
- **Keep it single** — then say what makes forty calls acceptable, and what the ceiling is.

What is not acceptable is shipping the single-lesson signature without a sentence saying it
was considered. That is how the N+1 becomes load-bearing.

## 7. Trap 4 — a contract-only task can still ship a lie

Generated types compile whatever you write. Nothing in this task can fail because a response
shape is wrong; the failure surfaces in WP10, after a frontend has been built against it.

So the bar is not "the spec is valid". It is **"P8.3, P8.4 and P8.5 can return exactly this
without changing it"**. Before you write each response schema, read the task that will
implement it:

- `GET /me/dashboard` — P8.5. Next activity **or an explicit "nothing started" state**, a
  due-review count that is present and zero until WP9, per-skill mastery. P8.4's trap says
  the new-learner case must not be `null` and must not be a 404, so the schema has to be
  able to *express* that state. A nullable `next_activity` with no discriminator cannot.
- `POST /attempts/{id}/submit` — P8.3. `GradeResult.Async` means the attempt can come back
  `pending` with no score. If `score` is required in the response schema, the async path is
  unrepresentable and Phase 3's AI graders are blocked by a YAML file.
- `GET /me/progress` — P8.5, across courses and skills.

Every one of those three is a shape that looks fine until the state it cannot express turns
up. Write the state machine down first.

## 8. What to build

### The contract package, first commit

`internal/modules/learning/contract/contract.go`, following the shape
`content/contract/contract.go` already uses — an `Aggregate` constant, the event topic
constants, the payload structs, then the interfaces.

Four types, exactly as `AGENT.md` §4 names them:

| Kind | Signature |
|---|---|
| interface | `ExerciseGrader` — `Grade(ctx, GradeRequest) (GradeResult, error)` |
| struct | `GradeResult` — `{Score, MaxScore, Correct, Feedback, Async, ReviewItems}` |
| interface | `ProgressReader` — `ProgressOf(ctx, userID, scope)` |
| interface | `UnlockChecker` — `IsUnlocked(...)`, per your Trap 3 decision |

Plus `GradeRequest`, `ReviewItem`, and the five published event payloads §4 lists
(`activity.completed`, `lesson.completed`, `course.completed`, `placement.completed`,
`learning.session_completed`).

**`GradeRequest` carries ids, not content.** WP8's P8.3 trap is blunt about it: passing the
whole content version couples every future grader to the content shape and makes the
interface impossible to widen. The grader reads what it needs through `content.Reader`.
This is the one thing in Phase 2 that Phase 3 cannot route around, and it is decided here,
not in P8.3.

### The spec, second commit

`api/openapi/components/learning.yaml` plus the eight paths, registered in
`openapi.yaml`'s `components.schemas` map the way `lesson.yaml` is (`openapi.yaml:3097-3115`
is the pattern).

```
POST /api/v1/courses/{id}/enroll            x-permission: self
GET  /api/v1/me/dashboard                   x-permission: self
GET  /api/v1/me/progress                    x-permission: self
POST /api/v1/activities/{id}/attempts       x-permission: self
POST /api/v1/attempts/{id}/submit           x-permission: self   + Idempotency-Key
GET  /api/v1/attempts/{id}                  x-permission: self
POST /api/v1/me/sessions                    x-permission: self
POST /api/v1/me/sessions/{id}/complete      x-permission: self
```

Then `make gen-backend`, `pnpm gen:api`, and `make docs` after updating the `learning` block
in `tools/docgen/data/learning.json` — endpoints, contract, decisions.

**The endpoint and contract tables in `AGENT.md` and `API.md` are generated.** Editing the
Markdown by hand looks like it worked until `make docs-check` fails in CI. P7.4 lost its
TODO checkboxes to exactly this and P7.5 nearly repeated it.

### What you should not need to touch

`.go-arch-lint.yml` already has `c_learning` and `m_learning`. If you find yourself editing
it, stop and re-read Trap 1 — the rules are not the thing that is wrong.

## 10. Definition of Done

Everything in [phase-2-plan.md](../phase-2-plan.md) §2.3, plus the five that have each cost a
round trip in this work package already:

1. **`make check` is not the whole check.** CI runs a second lint pass that it does not:

   ```bash
   golangci-lint run --build-tags=integration ./...
   ```

2. **Generated is generated.** `AGENT.md`, `API.md` and `DECISIONS.md` blocks come from
   `tools/docgen/data/learning.json` via `make docs`. So do `server.gen.go`,
   `client.gen.go` and `web/src/types/api.ts`. Commit all of it — `make gen-check` compares
   against git, so uncommitted generated output reads as staleness.

3. **One task, one diff.** The spec commit lands before the commit that mirrors it in Go.
   Formatting sweeps and tool configuration go in their own commit, or not in this branch.

4. **A test that cannot fail is not a test.** This task has almost nothing to test, which is
   the honest answer — say so. Do not pad it.

5. **A suppression comment is a claim.** `#nosec`, `//nolint`, `eslint-disable`. Three have
   shipped in Phase 2 so far; one was caught by CodeQL rather than by review.

Before you finish:

```bash
make check
golangci-lint run --build-tags=integration ./...
make gen-check
make docs-check
```

`make cover-check` needs Postgres and Redis. On a machine where 5432 and 6379 are taken,
run throwaway containers on other ports and point `TEST_DATABASE_URL` and `TEST_REDIS_ADDR`
at them rather than stopping whatever holds the ports.

## 11. What this task does **not** do

- **No handlers, no service, no repository, no `module.go`.** P8.3 builds the engine.
- **No migration.** P8.2 owns the `learn` tables, including the monthly partitioning of
  `attempts` and its pre-created partitions.
- **No grader registry.** P8.3, and it is validated at startup there.
- **No placement.** Phase 4. The table arrives empty in P8.2 because a second migration
  costs more than an unused table.
- **No `srs` contract.** P9.1 owns `srs/contract`, even though `ReviewItem` is about to
  point at it conceptually. Trap 1.
- **No change to `lesson`.** If the Trap 3 decision is to batch, `lesson` adopts the new
  signature when `learning` can actually answer it — not in this diff, which has no
  implementation to adopt.
