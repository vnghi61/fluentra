## 1. Why this work package is different

Everything else in Phase 2 is judged by a test. This one is judged by a learner opening the app
on a 320 px phone, in Vietnamese, with an empty account — which is the **common** case during
the alpha, not an edge case.

The backend is finished and honest: it returns `not_started` states, absent fields and real
zeros rather than plausible ones. The failure mode available to this work package is to paper
over that honesty with cards that say `0 XP` and skills that show 0 %, and then have to
un-ship them.

The bar: **a learner who has enrolled in nothing can tell what to do next, and every number on
screen is a number the API actually returned.**

## 3. The five rules, for every task here

1. **No hand-written DTOs.** Types come from `pnpm gen:api`. A PR that declares its own
   `interface DashboardResponse` is rejected however tidy it looks — Phase 1 shipped two schema
   mismatches into the E2E suite exactly that way.
2. **Empty, loading and error states ship in the same PR** as the happy path.
3. **Bundle figure in the PR body**, before and after, from `pnpm run build`. The budget is
   200 kB gzip and CI enforces it.
4. **Both locales.** Every string in `en.json` and `vi.json`. Vietnamese runs 20–30 % longer
   than English, which is a 320 px layout problem rather than a translation one.
5. **Accessibility in the PR, not in a later phase**: keyboard path, visible focus, no
   colour-only status, 44 × 44 targets. The `mobile-baseline` lint rules already enforce the
   last two.

---

## 4. Trap 1 — the API is honest and the mock is not

Three shapes in the responses will break a screen written against an imagined version:

- **`state` is an enum, and `next_activity` is absent rather than null.** `DashboardResponse`
  carries `not_started`, `in_progress` or `completed`; in two of the three the object is not
  there at all. A component that reads `data.next_activity.title` behind a truthiness check on
  `state === "in_progress"` is right; one that assumes null is a bug that only fires for a new
  learner, which is the most common learner during the alpha.
- **Arrays are always present, never null.** `skill_mastery`, `courses` and `skills` are
  required and the backend ships `[]`. Do not add a defensive `?? []` and then rely on it —
  if one of them ever arrives as null that is a backend bug worth failing loudly on.
- **`due_reviews_count` is a real field with a temporarily fixed value.** Not a placeholder to
  hide. See §2.

Test the states against a fixture generated from `types/api.ts`, not against a hand-written
object literal that agrees with the component.

---

## 5. Trap 2 — the submit path is idempotent and the UI can defeat it

`POST /attempts/{id}/submit` requires the `Idempotency-Key` header, and the backend enforces
one grade per attempt with a conditional claim in SQL: two concurrent submissions with the same
key grade once and return the same body.

What that buys is only real if the client sends **one key per submission attempt**, generated
when the learner presses the button and reused on every retry of that same answer. A key
regenerated inside a retry handler turns a retry into a second submission, which the backend
correctly refuses as a conflict — and the learner sees an error for a thing that worked.

Acceptance for P10.3 is the two-tab test: open one lesson in two tabs, submit in both, exactly
one attempt is graded and both tabs render the same result.

---

## 6. Trap 3 — the review grade is an enum, and the keyboard is 1–4

P9.1 defines the wire format as `again`, `hard`, `good`, `easy`. The keyboard shortcut map is
1–4 because that is what fingers do on a flashcard. Sending the digit is the mistake this trap
exists to name: it type-checks against a loose schema, and it silently mis-grades every review
in the alpha.

The generated types make the enum non-negotiable if you use them. That is the fourth reason for
rule 1.

---

## 7. Trap 4 — three cards, not six, and "not started" is not 0 %

The UI mock has six dashboard blocks and three of them read `gamification` tables that do not
exist in Phase 2: Today's Goal (XP), Achievement Preview, and the streak. The review's §A1
settled this: the Phase 2 dashboard is **Continue Learning, Reviews Due, Skill Progress**.

Adding a streak table to `learn` to fill the gap fails rule DB1, and rendering a permanent zero
is worse than rendering nothing, because the frontend builds a card around it and the card
ships lying.

The same reasoning applies on the progress screen: a skill with no Phase 2 data renders "not
started yet", which is true, rather than 0 %, which reads as failure.

## 8. The tasks

### P6.4–P6.6 — the shell the screens hang on

**Do.** The app shell, the route registration pattern, and the feature-slice scaffold, per
[WP6-design-system.md](WP6-design-system.md). Check its state table against the tree first: the
primitives have moved since it was written, and what remains is probably the shell, the routes
and the scaffold rather than the tokens or the primitives.

**Acceptance.** A new route renders inside the shell with the nav in place, lazily, and a new
feature slice can be created by copying `features/auth/`'s four-file shape without editing the
router by hand more than once.

### P10.1 — dashboard

**Do.** Three cards in this order: *Continue Learning* — the hero, one primary action, driven
by the next-activity value; *Reviews Due* — count, estimated minutes, one button; *Skill
Progress* — per-skill mastery from the same response. No Quick Practice grid: it duplicates the
Practice tab, so fold it into the Reviews Due empty state ("nothing due — practise anyway").

**Acceptance.** Four states, each with a test: brand-new learner with no enrolment, learner
mid-course, learner with nothing due, API error. The greeting does not claim a name the API
does not return. 320 px clean in `en` and `vi`.

**Trap.** §7, and §4's first bullet — the `not_started` state is the one that renders most
often in the alpha and the one most easily written as a crash.

### P10.2 — learn: catalogue, unit list, lesson detail

**Do.** `/learn` renders the course with a progress bar, its units, and the lessons in each. A
**unit list, not a vertical node map** — the map is deferred deliberately (review §D2): roughly
five times the build, for an audience of adult exam-preppers who want a syllabus. Two states
carry the weight, *done* and *next*, with `available` as the default and `locked` shown as a
row with a lock icon **and the reason string the API returns**.

That string is real: `lesson` composes it from the prerequisite lesson titles ("Complete Unit 2
Lesson 1 and Unit 2 Lesson 3 first"), and P8.4 made the lock verdict behind it real too.

**Acceptance.** A learner answers, without scrolling twice: where am I, what is next, what is
done, what is locked and why. Status is never conveyed by colour alone. An empty course renders
an intentional state — content seeding (P11.1) runs in parallel, so a partial course is the
normal case for weeks.

### P10.3 — lesson runner

**Do.** Full-screen and distraction-free. Header: exit and lesson title. Then a step counter and
progress bar, the activity canvas, one primary action. **Three exercise types only**: multiple
choice, gap-fill, flashcard — they cover the seeded content, and a fourth is added when content
needs it. Exit asks for confirmation. Completion shows score, accuracy and time.

**Acceptance.** The two-tab test in §5. Keyboard: an answer can be selected and submitted
without a mouse. A submit failure keeps the learner's answer on screen and offers a retry rather
than dropping it. The completion animation honours `prefers-reduced-motion`. No XP and no long
celebration.

### P10.4 — review session

**Do.** Queue, flashcard, reveal, grade, next. The front shows the word, its IPA and a listen
button; the back shows the sense and examples — exactly the fields P9.4 stores. Four grade
buttons: Again, Hard, Good, Easy. Space flips, 1–4 grades, with a hint shown on first use and
never again. Session summary at the end.

This is the one screen that needs a Track A task first: build it against the generated types
from P9.1 and MSW handlers, and finish it against P9.3's endpoints.

**Acceptance.** A full queue clears with the keyboard alone. Grade buttons are at least
44 × 44 px and distinguishable without colour. **The four labels fit at 320 px in Vietnamese** —
check that specifically; it is the tightest row in the app. Audio failure degrades to a disabled
button with a title, never a broken control.

**Trap.** §6. The digits are an affordance; the enum is the contract.

### P10.5 — progress

**Do.** Total study time, words mastered, and per-skill progress across vocabulary, grammar,
listening and speaking, reading `GET /me/progress`. The endpoint returns per-course counts,
percentages and per-skill mastery; render what it gives.

**Acceptance.** No XP, no streak, no achievements tab, no leaderboard, no radar chart. A learner
with no history sees an intentional empty state. Skills with no Phase 2 data say "not started
yet".

**Trap.** This is the screen most likely to grow a chart library, and a charting dependency can
eat most of the remaining bundle headroom in one install. Bars built from the existing
`progress` primitive are enough for four skills.

- Every screen renders empty, loading and error states
- The 320 px no-horizontal-scroll spec passes in **both** `en` and `vi`

- The review queue can be cleared entirely from the keyboard
- No hand-written response type anywhere under `web/src/features/`
- No `streak`, `xp`, `daily_goal` or `achievements` rendered anywhere

## 11. What this work package does **not** do

- **No gamification surfaces.** No streak, XP, daily goal, badges or leaderboard.
- **No speaking or writing screens.** Those modules are Phase 3.
- **No vertical path map.** Deferred with a reason; build it after the alpha if learners ask.
- **No review forecast screen.** The endpoint may not even be implemented — see P9 §7.5.
- **No chart library.**
- **No new API paths.** If a screen needs one, that is a spec change and a backend task.
- **No E2E journeys.** Those are P11.2, after the screens and the seeded content both exist.
