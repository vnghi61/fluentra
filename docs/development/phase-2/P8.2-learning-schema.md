## 2. `audit` already did this. Read it before you write anything

WP8 describes monthly partitioning as though it were new to the repository. It is not.
`audit.audit_logs` and `audit.security_events` have been partitioned by month since
`1700000030`, with a creation function, a retention function, a cron job and an integration
test. Almost every decision this task faces is already made there, and the ones you should
copy are:

| | `audit` does | Why it matters here |
|---|---|---|
| Primary key | `PRIMARY KEY (created_at, id)` | PostgreSQL requires every partition-key column in the primary key. `attempts` cannot have `PRIMARY KEY (id)` |
| Indexes | declared on the parent table | partitions inherit them; declaring per-partition means the job has to create them too, forever |
| Creation | `audit.ensure_partitions(months_ahead integer) RETURNS integer` | idempotent by `to_regclass(...) IS NOT NULL THEN CONTINUE`, so re-running is free |
| Time zone | `date_trunc('month', (now() AT TIME ZONE 'UTC'))` | the same call from a worker in another region must produce the same boundary |
| Naming | `audit_logs_y2026m08` | see below — **not** what WP8 says |
| Retention | `DETACH`, never `DROP` | instant and reversible; dropping is neither |

Two places where copying it would be **wrong**:

- **The grant dance.** `audit` does `REVOKE ALL` then `GRANT SELECT, INSERT` on each new
  partition, because `audit_logs` is append-only and the schema's default privileges are
  wider than that. `learn`'s default privileges are exactly what `attempts` needs
  (`_bootstrap/1700000000` line 90). Copying the REVOKE would make attempts unwritable, and
  it would do it a month after deploy, in a partition nobody had inserted into yet.
- **Retention.** `audit` detaches partitions older than two years because BR-AUDIT-05 says
  so. Nothing says that about attempts, and an attempt is a learner's own history. Do not
  invent a retention policy. Create the partitions; leave them.

**Naming.** WP8 says `attempts_YYYY_MM`. The repository's convention is `_yYYYYmMM` —
`attempts_y2026m08` — and `audit.detach_expired_partitions` parses it with
`'_y(\d{4})m\d{2}$'`. Follow the repository. If you prefer WP8's spelling, say why in the PR;
what is not acceptable is a second convention nobody chose.

## 3. Trap 1 — a unique index on a partitioned table cannot enforce global uniqueness

This is the expensive one, and it is P8.3's problem created by P8.2's schema.

PostgreSQL requires every unique or primary key constraint on a partitioned table to include
all partition key columns. So on an `attempts` partitioned by month, the strongest constraint
you can write is:

```sql
UNIQUE (idempotency_key, created_at)   -- enforced per partition, not globally
```

Two submissions carrying the same `Idempotency-Key`, one on 31 August and one on 1 September,
land in different partitions and **both succeed**. P8.1 made that header required and
`learning/DECISIONS.md` records it as part of the HTTP contract; P8.3's acceptance is that a
double submit with the same key grades **once**, proven with two concurrent goroutines. A
constraint that holds only within a calendar month does not give P8.3 anything to rely on.

There is no obviously right answer, so decide and record it in `learning/DECISIONS.md`:

- **A separate, unpartitioned table** — `learn.attempt_submissions` or similar, keyed on the
  idempotency key, with a real global unique constraint and a foreign key to nothing (see
  below). Costs a table and an insert; buys an actual guarantee. Remember it needs a row in
  the `tables:` front-matter.
- **Scope the key to the attempt.** A submission always names one attempt, and an attempt row
  lives in exactly one partition, so `UNIQUE (id, idempotency_key)`-shaped reasoning can be
  made to work — but write down *why* it works, because "the attempt is in one partition" is
  the entire argument and it is not obvious.
- **Do not** rely on `ON CONFLICT` against a partition-local unique index and describe it as
  idempotent. That is the version that passes P8.3's test in September and fails in
  production on 1 October.

State the window your choice leaves, if any. "It is idempotent" without a scope is the claim
this trap exists to catch.

## 4. Trap 2 — the partition-creation function must hide `CREATE TABLE` from the drift checker

`tools/docgen/check-drift.mjs` step 2 regex-matches table declarations in
`db/migrations/<module>/` against the module's `tables:` front-matter. A `format()` template
containing the literal words `CREATE TABLE` reads to it as a table you failed to document,
and the docs job fails on a table that does not exist.

`audit` solved it by concatenating the keyword out of the format string, and left the comment
explaining why:

```sql
EXECUTE 'CREATE TABLE ' || format(
    'audit.%I PARTITION OF audit.%I FOR VALUES FROM (%L) TO (%L)',
    partition_name, parent_name, starts_at, ends_at);
```

Copy the shape and the reason. Finding this from the failure message costs an hour.

## 5. Trap 3 — WP8 says "River job". This repository schedules with advisory locks

WP8 says "the background partition-management job is created alongside it" and calls it a
River job. River is in the repository and `cmd/worker` builds `river.NewWorkers()`, but
periodic maintenance does not go through it. The mechanism is `internal/platform/job`:

```go
type CronJob struct {
    Name     string
    LockID   int64
    Interval time.Duration
    Task     func(ctx context.Context) error
}
```

A module exposes `CronJobs() []job.CronJob` and `cmd/worker/main.go` registers them —
`audit` is the worked example, at `internal/modules/audit/module.go:144` and
`cmd/worker/main.go:347`. The lock is a Postgres advisory lock, so two worker replicas do not
both rotate.

**Pick a lock id and check it is free.** The convention is the module's migration number:
`audit` is `1_700_000_030`/`_031` for migration `1700000030`, so `learning` is
`1_700_000_210`. Grep before you commit — `1_700_000_050` is currently declared twice, by
`internal/modules/user/job/deletion.go` and `internal/platform/job/outbox_retention.go`, so
those two jobs silently serialise behind each other. Do not add a third.

## 6. Trap 4 — pre-created partitions are half of it. The other half is the call at start-up

WP8's trap is right and does not go far enough:

> Monthly partitioning with no initial partitions causes immediate runtime failure on insert,
> and no automatic partition creation is a production outage on the 1st of a month.

There is a third failure, and `audit` carries the comment that names it: a deploy onto a
database whose partitions have **already lapsed** — a staging box left alone for a quarter, a
restored backup — refuses writes until the first cron tick. So the module exports the
rotation and `cmd/worker` calls it once at boot, logging rather than failing:

```go
if err := trail.RotatePartitions(ctx); err != nil {
    slog.ErrorContext(ctx, "could not rotate audit partitions at start-up; the scheduled job will retry", ...)
}
```

Three things, all in this task: partitions in the migration, the cron job, and the start-up
call. The migration alone passes every test you are likely to write and fails on 1 September.

## 7. What to build

### The migration — `db/migrations/learning/1700000210_create_learning_tables.sql`

Goose up/down, reversible, following `db/migrations/lesson/1700000200` for house style:
`IF NOT EXISTS`, named constraints, `ck_`/`uq_`/`fk_`/`idx_` prefixes, checks on every enum
column rather than a Postgres `ENUM` type.

| Table | Notes |
|---|---|
| `enrollments` | learner ↔ course. `user_id → core.users(id)` (DB4's one permitted exception), `course_id → learn.courses(id)` — same schema, so a real key, not the bare uuid `activities.content_version_id` had to use |
| `progress` | `UNIQUE (user_id, scope, scope_id)` as `uq_progress_user_scope`. Not partitioned, so this is an ordinary unique index. It is the read path for every dashboard request in the product |
| `attempts` | `PARTITION BY RANGE (created_at)`, PK including the partition key, partitions for this month and the next two, indexes on the parent |
| `learning_sessions` | `user_id`, `started_at`, `ended_at`, `activities_completed`, `minutes` |
| `placement_results` | created empty. Phase 4 fills it; a second migration later costs more than an unused table now |
| `skill_mastery` | `user_id`, `skill`, `level`, `confidence`, `updated_at`. Unique per `(user_id, skill)` — P8.4 updates it incrementally, so the upsert needs something to conflict on |

Plus `learning.ensure_partitions(...)`, modelled on `audit.ensure_partitions`.

`AGENT.md` §5 names two indexes to get right now rather than later:
`idx_attempts_user_activity_time` and `idx_attempts_activity_time`.

## 9. Definition of Done

Everything in [phase-2-plan.md](../phase-2-plan.md) §2.3, plus the five that have each cost a
round trip in this work package:

1. **`make check` is not the whole check.** CI also runs

   ```bash
   golangci-lint run --build-tags=integration ./...
   make gen-check
   ```

   `gen-check` compares generated output against git, so sqlc output you ran but did not
   commit reads as staleness.

2. **Generated documentation is generated.** `AGENT.md`, `API.md`, `DECISIONS.md` and the
   TODO checkboxes come from `tools/docgen/data/learning.json` via `make docs`.

3. **One task, one diff.** Tool configuration — `sqlc.yaml`, `.go-arch-lint.yml` — is
   arguably its own commit; at minimum it is its own commit *message*. P8.1 split spec from
   Go for the same reason.

4. **A test that cannot fail is not a test.** The partition test is the one to check hardest:
   a test that inserts a row dated *today* passes with or without next month's partition.
   Insert into next month, and confirm the test fails when the partition is missing.

5. **A suppression comment is a claim, and one in this schema's neighbour is currently
   false.** `internal/modules/lesson/repository/repository.go` carries seven
   `//nolint:gosec // bounded integer` on `int32(...)` conversions of `estimated_hours`,
   `position` and `estimated_minutes` — none of which the spec bounds. P7.5 fixed exactly
   this for `weight` by bounding it in `openapi.yaml` and in the domain; the other three were
   not in that diff's scope. Do not add an eighth. If you convert a width here, either the
   value is bounded somewhere a reader can find, or it is not bounded.

`make cover-check` and the integration suite need Postgres and Redis — see **Ports** in
[README.md](README.md) if 5432 or 6379 is already taken on your machine.

## 10. What this task does **not** do

- **No service, no repository layer, no handlers.** P8.3 builds the engine; the eight paths
  from P8.1 stay unimplemented.
- **No grader registry.** P8.3, validated at startup there.
- **No retention or archival for `attempts`.** Nothing asks for it, and a learner's history
  is not an audit log.
- **No placement logic.** The table only.
- **No change to `lesson`.** Its tables live in the same schema and are not yours. The
  batched `UnlockChecker` is adopted in P8.4, not here.
