## 1. Why this one is different

`ExerciseGrader` is implemented once in WP9 and five more times in Phase 3 by `grammar`,
`reading`, `listening`, `speaking` and `writing`. ADR-0015 exists because roughly 70 % of six
skill modules was going to be identical; this task is the 70 %.

The interface shape landed in P8.1 and is merged. What lands here is the machinery behind it,
and WP8 is blunt about the stakes: getting `GradeRequest` wrong is *"the one thing in Phase 2
that Phase 3 cannot route around"*.

So the bar for this task is not "the tests pass". It is **"a Phase 3 agent implementing the
fifth grader adds a file and changes nothing else"**.

## 3. Trap 1 — you are handed an activity id, and `lesson` will not tell you what it is

This is the structural problem in the task, and it is worth finding now rather than three
hours in.

`POST /activities/{id}/attempts` gives you an **activity id**. To do anything at all you need:

| You need | For | `lesson/contract.Reader` gives you |
|---|---|---|
| activity → `kind` | choosing the grader from the registry | **nothing** |
| activity → `content_version_id` | building `GradeRequest` | **nothing** |
| activity → `lesson_id` | the progress rollup | **nothing** |
| lesson → `unit_id` | the rollup | `GetLesson(id).UnitID` ✅ |
| unit → `course_id` | the rollup and `course.completed` | **nothing** |

`Reader` is `GetLesson`, `ListLessons`, `NextLesson`. `GetLesson` does return the lesson with
its `Activities` populated — but you cannot call it, because you have an activity id and not
a lesson id. Two hops of the chain the task is graded on are unreachable.

**The wrong fix is the easy one.** `attempts.activity_id` has a real foreign key to
`learn.activities`, `lesson` and `learning` share the `learn` schema, and sqlc would generate
a join without a murmur. **Nothing automated would catch it**: there is no SQL linter in this
repository, `go-arch-lint` does not read SQL, and `check-drift` only compares migrations to
front-matter. DB1 and DB2 would be broken by a query nobody's tooling can see, in the module
ADR-0015 wrote to stop exactly that kind of shortcut.

So `lesson/contract.Reader` has to grow. That is legitimate and expected — P8.1 grew
`learning`'s contract for `lesson`'s benefit; this is the same trade in the other direction.
Two things about how:

- **One call, not three.** A `GetActivity` plus a `GetUnit` plus a `GetLesson` is three round
  trips per attempt start, on the hottest path in the product. This work package has already
  paid for the single-item habit twice — `content.Reader.GetManyVersions` in P7.4 and the
  batched `UnlockChecker` in P8.1. Prefer one method that resolves an activity to everything
  its position implies, and say what it returns in `lesson`'s own contract docs.
- **The change to `lesson` is part of this PR**, including its `AGENT.md` §4 table (generated
  — `tools/docgen/data/learning.json`, then `make docs`) and a test in `lesson` that the new
  method returns what it claims. A contract grown without a test in the owning module is a
  promise the owner has not made.

Record the decision in `learning/DECISIONS.md`, and say in the PR that `lesson`'s contract
changed, because reviewers of a `learning` PR do not expect it to.

## 4. Trap 2 — the registry fails the process, not the learner

ADR-0015's compliance section is one sentence long and half of it is this: *"The grader
registry is validated at startup."*

An activity kind with no registered grader must **fail `cmd/api` at boot, with the kind named
in the error**. Not a 500 at 22:00, not a log line, not a nil grader that panics on the first
learner who reaches that activity.

Which raises the question the acceptance turns on: *validated against what?* The set of kinds
that exist is a property of the data — `learn.activities.kind` is free text bounded only by
length. Two honest readings:

- **Registry-complete**: every kind present in the database has a grader. Correct, and it
  means `cmd/api` reads the database at boot, and that an author adding an activity of a new
  kind can stop the next deploy.
- **Registry-declared**: the module declares the kinds it supports, and an attempt on an
  unknown kind is a clean 422 with the kind named. Startup validation then checks the
  declared set against the registered graders — a wiring mistake fails the boot, unknown data
  fails one request.

Pick one and record it. What the acceptance will not accept is a registry that silently
returns `nil` for an unknown kind, whichever reading you chose.

Phase 2 has **no real grader**. WP9 writes the first. So the fake grader lives in
`learning/domain/` — WP8 says so explicitly — and it is what the lifecycle tests dispatch to.
A fake in `domain/` rather than in a `_test.go` file is deliberate: WP9 and Phase 3 need
something to develop against.

## 5. Trap 3 — `GradeRequest` carries ids. Every convenience you add costs six modules

The temptation, on writing the first grader, is to put the resolved content version into
`GradeRequest` so the grader does not have to fetch it. WP8:

> That couples every future grader to the content shape and makes the interface impossible to
> widen. Pass ids and let the grader read what it needs through `content.Reader`.

`GradeRequest` is already merged with `AttemptID`, `ActivityID`, `ContentVersionID`, `UserID`
and `Response`. **Do not add a field to it in this task.** If grading genuinely cannot be done
from those five, that is a finding worth stopping and raising, not a field worth adding
quietly — because the shape is what five Phase 3 modules inherit.

The same applies to `GradeResult`. `ReviewItems` is emitted here even though nothing consumes
it until WP9; that is not dead code, it is the contract being honoured before its consumer
exists.

## 6. Trap 4 — idempotency is already decided, and the test has to race

P8.2 left you the mechanism and the reasoning, in the comment above
`ClaimAttemptForGrading`:

- a unique constraint on a partitioned table must include the partition key, so
  `UNIQUE (idempotency_key)` is not available;
- the invariant that is enforceable is **one attempt row is graded at most once**;
- `AND status = 'in_progress'` in the claim makes the database the arbiter.

Your job is to use it, not to re-solve it:

- the winner grades and writes the result;
- the loser gets no rows, reads the attempt back, and returns the **stored result** when the
  `idempotency_key` matches — the same response body, not a fresh grade;
- a *different* key against an attempt already claimed is a conflict, not a retry.

**The test races two goroutines.** WP8's acceptance says so in as many words, and a
sequential double-submit passes with the guard removed.
`db/migrations/learning/schema_integration_test.go` already has the shape at the SQL level;
yours runs through the service, and it must fail if the claim's status guard is removed.

Note what `ClaimAttemptForGrading` does *not* do: it does not check that the caller owns the
attempt. `attempts.user_id` is on the row and the actor is in the context. An idempotency key
is not an authorisation token.

## 7. Trap 5 — `Async` has no implementation and still has to work

Every Phase 2 grader is synchronous. `GradeResult.Async` exists for Phase 3's AI graders, and
WP8 requires it honoured **now**: the attempt stays in `grading`, no score is written, and the
response is the 202 that `components/learning.yaml` already documents. `learning/AGENT.md` §4
lists `writing.graded` and `speaking.scored` as events this module consumes to complete such
an attempt later — **do not subscribe to them in this task**; nothing publishes them, and a
consumer for an event that cannot arrive is untestable.

What this task owes the flag is that the *path exists and is exercised*: a fake grader
returning `Async: true` leaves the attempt in `grading`, the endpoint answers 202, and
`GET /attempts/{id}` reports it. That is three assertions and it is the difference between a
flag that works in Phase 3 and a flag that is discovered to be decorative in Phase 3.

## 8. Trap 6 — the rollup is one transaction, and it publishes more than one event

Submit does, in order: claim → dispatch → persist the attempt → roll progress up
activity → lesson → unit → course → publish. WP8 requires the rollup in **one transaction**;
`dbx.InTx` is the helper and `lesson/service/service.go` has the pattern.

Events go to the outbox **inside that transaction**, through `shared/outbox` — `lesson`'s
`outboxWriter` adapter at `module.go:205` is four lines and is the shape to copy. That is what
makes "graded" and "activity.completed" atomic; publishing after commit reintroduces the
partial failure the outbox exists to remove.

`activity.completed` always. `lesson.completed` and `course.completed` **only when the rollup
crosses those boundaries** — a table-driven test on the crossing is worth more than one on the
happy path, because the boundary case is where a learner sees a course congratulate them at
lesson three.

One naming hazard from the handoff notes: `lesson.published` belongs to `lesson`,
`lesson.completed` belongs to you. Different aggregates, same prefix.

## 9. What to build

Follow `lesson`'s layering — `domain/`, `service/`, `repository/`, `transport/http/`, wired in
`module.go` — even though `m_learning` is a single arch-lint component rather than four. The
component granularity is a linting decision; the package structure is a readability one, and
`learning/AGENT.md` §7 already documents the folders.

| | |
|---|---|
| `domain/` | attempt state machine, the rollup rules, the fake grader, the registry type, module errors in `shared/apperr` |
| `service/` | the lifecycle, `dbx.InTx`, outbox writes, dispatch |
| `repository/` | the sqlc queries from P8.2 behind an interface the service declares |
| `transport/http/` | three handlers, the `Idempotency-Key` header, `x-permission: self` |
| `module.go` | `New(Deps)`, registry validation, `Routes` |
| `cmd/api` | construct and mount it — it is not constructed there at all today |

Errors get codes, and the codes go in `learning/AGENT.md`'s error table and in
`learning.json` for the generated blocks.
