## 1. Why this one is different

Everything the dashboard renders was computed by P8.3 and P8.4. This task adds no rule, no
event and no table. What it adds is a **budget**: WP8's acceptance for P8.5 is

> One dashboard request issues a bounded number of queries — assert the count; this endpoint is
> hit on every app open and an N+1 here is the first performance bug of the alpha.

So the deliverable is not "the endpoint returns the right JSON". It is "the endpoint returns
the right JSON **in a number of queries that does not grow with the number of lessons and
activities a learner's course holds**, and a test says so in numbers". §4 has the exact budget,
including the one read P8.4 leaves proportional to unit count and what you may do about it.

The second half of the task is restraint. The UI mock has six blocks; three of them have no
data source until Phase 3. Shipping a plausible zero for those is worse than shipping nothing,
because the frontend builds a card around it and the card ships lying.

## 3. Trap 1 — `total_activities` is not a number this module can count

`CourseProgress` is required to carry `completed_activities`, `total_activities` and
`percentage`. `learn.progress` stores one row per scope with `scope_id`, and **nothing on an
activity-scope row says which course the activity belongs to**. So both halves of that
fraction need `lesson`, and this is the same shape of problem P8.3 and P8.4 each hit once:

| You need | Owner | Available through the contract today |
|---|---|---|
| Every activity id in a course | `lesson` | **no** |
| Which of them this learner completed | `learning` | yes — `ListProgressByUserScopeAndIDs` |

The tempting resolutions are both wrong:

- **Walking the tree.** `ListUnitsByCourseID`, then `ListLessons` per unit, then `GetLesson`
  per lesson to see its activities: one read per lesson in the course, on the endpoint whose
  acceptance is a query count. P8.4 §7 removed exactly this walk from next-activity
  resolution; do not reintroduce it one endpoint later.
- **Reading `learn.activities` from `db/queries/learning/`.** Same schema, so sqlc would
  generate it without complaint, and nothing in CI would catch it — no SQL linter, and
  `go-arch-lint` does not read SQL. It is still another module's table (DB1).

The right move is the one P8.3 and P8.4 both took: **`lesson`'s contract grows one batched
method**, over all the learner's enrolled courses at once, and `lesson` answers it from its
own tables. It is close to free there — `db/queries/lesson/activities.sql` already has
`ListActivitiesByLessonIDs`, and `ListLessonsByCourseID` already exists behind `NextLesson`.

Whether that method returns the activity ids per course, or counts plus the ids you need for
the numerator, is yours to choose — but say which in `DECISIONS.md`, and make it take
**course ids, plural**. A learner in three courses must not cost three calls.

Two details that will otherwise be found by a divide-by-zero:

- A course with no activities has no percentage. Decide what `0/0` renders as and test it.
- `percentage` is an integer in the spec, and its example is `12/40 → 30`. Say how you round.

## 4. Trap 2 — the query count is the acceptance, so count what P8.4 already costs first

"A bounded number of queries" is only a testable claim once you say what a query is, and once
you know what the endpoint costs before you touch it. The machinery is already in the test
suites and cost P8.3 and P8.4 to build:

- `fakeLearningRepo.queryCounter` (`service/service_test.go`) counts repository calls;
- `fakeLessonReader.calls` / `callCount(method)` counts contract reads per method, added in
  P8.4 for precisely this kind of assertion.

`NextActivity`, as P8.4 left it, costs this per dashboard request:

| Read | Times |
|---|---|
| `ListEnrollmentsByUser` | 1 |
| `ListUnitsByCourseID` | 1 |
| `ListLessons` | **once per unit in the course** |
| `ListProgressByUserAndScope` (lesson scope) | 1 |
| `GetLesson` | 1 — only the chosen lesson |
| `ListProgressByUserScopeAndIDs` (activity scope) | 1 |

So the endpoint is already constant in the number of **lessons and activities** — which is what
P8.4 §7 bought — and still linear in the number of **units**. A 12-unit course costs nine more
`ListLessons` calls than a 3-unit one, and that is the state of the code you inherit, not a
regression to find.

Two honest readings of "bounded", and the acceptance takes either:

- **Inherit it.** The dashboard stays linear in units and constant in everything else. Then the
  fixtures that prove it differ in *lessons per unit*, not in unit count, and the PR states the
  per-unit read as a known cost.
- **Collapse it.** The batched method §3 adds for activity ids can return the course's ordered
  lessons in the same call, and next-activity resolution reads from that instead of walking
  units. The whole request becomes a fixed number of reads regardless of course shape. This is
  the better endpoint and it is explicitly permitted — see §12 for what it does *not* license.

Whichever you take, say the number in the PR, and assert **per method, not in aggregate**.
`GetLesson: 1` is a fact about the design; `total: 6` is a number someone will "fix" by moving
work into a loop inside a single method.

`/me/progress` has no excuse in either reading: enrolments, one batched `lesson` call, one
progress read and one mastery read answer it for a learner in any number of courses. If it
grows a per-course read, that is the N+1 arriving through the quieter endpoint.

## 5. Trap 3 — a cached dashboard is a dashboard that lies right after a submit

`learning/AGENT.md` §12 already names the keys, the TTLs and what invalidates them:

```
fluentra:{env}:learning:dashboard:{user_id}:v1        2 min   any completion event
fluentra:{env}:learning:progress:{user_id}:{course_id}:v1   5 min   activity.completed
fluentra:{env}:learning:unlock:{user_id}:{lesson_id}:v1     10 min  lesson.completed
```

That table is generated from `tools/docgen/data/learning.json`. It currently describes
something no code does. Either the code catches up in this task, or the table does — a
documented cache that does not exist is worse than no cache, because the next agent reasons
about invalidation that nobody wrote.

The hazard specific to this endpoint: **the dashboard changes on the learner's own write**. A
2-minute TTL with no invalidation means finishing an activity leaves it displayed as the next
thing to do, on the screen the learner returns to immediately after finishing it. So the submit
path invalidates the key, and `lesson` has already settled how (`invalidateLessonCaches`,
`service.go:867`):

- invalidate **after** the transaction commits, never inside it — a rollback that has already
  dropped the cache is a cache that lied in the other direction, briefly;
- a failed invalidation is **logged, not returned**: a Redis outage must not fail a submit;
- reads go through `Cache[T].GetOrLoad`, which falls through to the loader when Redis is down.

Two smaller ones, neither in the handoff notes. Every key carries the `user_id`,
and a cached dashboard must never be reachable by another learner's request — that is the one
cache bug in this product that is a data leak rather than a stale number. And `cmd/api` passes
`deps.Redis`, which is nil in tests: `newLessonCaches` returns a zero-value struct in that case, and
every read site in `lesson` guards the field — `if s.caches.Tree == nil { … }` at
`service.go:521`, and four more like it — before touching the cache. Those guards are written,
not inherited: a nil `cache.Cache[T]` is a nil interface, and calling `GetOrLoad` on it panics
the request.

If you leave the unlock key unimplemented — it is not required by any acceptance below —
remove it from `learning.json` or mark it deferred in `TODO.md`. Do not leave it claimed.

## 6. Trap 4 — `due_reviews_count` is zero, and reaching for the real number breaks the boundary

The field is in the spec and the frontend renders it as the "Reviews Due" card. `srs` has
`internal/modules/srs/contract/` containing exactly one file, `doc.go` — **there are no types
there yet**. WP9 P9.1 writes them.

So the dashboard returns a literal zero, and the PR says so. Specifically, do not:

- add `c_srs` to `m_learning_service` in `.go-arch-lint.yml` to prepare for WP9. The module
  edge exists at `m_learning` already; the service edge is WP9's change, in WP9's diff, with
  WP9's test;
- invent a `ReviewReader` interface in `learning` for `srs` to implement later. P8.1 owns the

- hide the field until WP9. It is `required` in `DashboardResponse`; removing it is a spec
  change.

Leave a comment at the zero saying which task fills it in. That is the difference between a
number that is honest and a number that is forgotten.

## 7. Trap 5 — `null` where the spec promises a list, and a field where the spec promises absence

Three ways the JSON can be wrong while every Go test passes:

- `skill_mastery` and `courses` and `skills` are **required arrays**. A Go `[]T` that is nil
  marshals to `null`, not `[]`, and a new learner is exactly the case where they are empty —
  the state the client renders most often during the alpha. Initialise the slices.
- `next_activity` is **absent**, not null, when there is nothing to do. That is `omitempty` on
  a pointer field, and the spec's own `notStarted` example shows the shape.
- `state` is `not_started | in_progress | completed`. `domain.NextActivityResolution` already
  carries exactly those strings; map them, do not re-derive them from progress rows, or the
  dashboard and next-activity resolution will disagree the first time one of them changes.

Test the three states against the response body, not against the DTO struct — marshal it. The
first two of these are invisible from the Go side.

`CourseProgress.status` is a fourth trap in the same family: its enum is
`not_started | in_progress | completed`, which is **not** the enrolment status enum
(`active | completed`, per P8.4's decision). One is about the learner's progress, the other
about the enrolment record. Map deliberately.

## 12. What this task does **not** do

- **No `srs` read.** WP9. The field is zero and says so (§6).
- **No streak, XP, daily goal or achievements.** Phase 3, and not in the `learn` schema.
- **No placement, no adaptive daily plan, no skill radar.** Phase 4 and Phase 3.
- **No change to the rules of next-activity resolution or the rollup.** P8.4 owns both. Making
  the resolution read from the batched `lesson` call this task adds (§4) is a change to *how it
  reads*, and is fine; changing *which activity it picks*, or when a scope counts as complete,
  is not. If the dashboard wants a different answer, that is a finding to raise, not a rule to
  re-implement here.
- **No new endpoint.** The eight paths were fixed in P8.1 and six are already implemented.
- **No `user.deleted` consumer**, and no event consumers at all — `learning` subscribes to
  nothing today and this task does not change that.
- **No new tables or columns.**
